# Tests Documentation

This directory details the testing strategy, frameworks, mocking conventions, and test running instructions for the project.

---

## 🧪 Testing Strategies

The project supports two levels of testing:
1. **Unit Tests**: Test individual functions (e.g., helpers, utility functions, business logic validation rules) in isolation by mocking external dependencies.
2. **Integration Tests**: Test the API controllers, middleware, and database layers by mocking database calls (or using local docker test databases) and utilizing Echo's HTTP test tools.

---

## 🛠️ Testing Tools

- **Standard Library `testing`**: Core test suite framework.
- **`httptest`**: For recording and asserting HTTP requests and responses.
- **`github.com/labstack/echo/v4`**: Echo router context integration in tests.

---

## 🏗️ Design Rules for Tests

1. **Isolation**: Tests should clean up their state. Do not leave records in shared databases or global states that cause subsequent tests to fail.
2. **Table-Driven Tests**: Use table-driven testing in Go where possible to test multiple inputs/outputs cleanly:
   ```go
   tests := []struct {
       name     string
       input    string
       expected int
   }{
       {"valid", "data", 200},
       {"invalid", "", 400},
   }
   for _, tc := range tests {
       t.Run(tc.name, func(t *testing.T) {
           // run assertion
       })
   }
   ```
3. **Mocks**: 
   - Mock database transactions using interfaces where possible.
   - For simple testing without a live database connection (like standard unit tests), ensure services accept interfaces (e.g., `db.Querier` generated by SQLC) so mocks can be easily swapped in.
4. **Validation Testing**: Always assert:
   - Response HTTP Status code (`rec.Code`).
   - Standard JSON structure deserialized into success/error DTOs.
   - Specific expected field values.

5. **📂 Directory Mirroring**:
   The `/tests` folder should mirror the `/internal` package structure for all integration tests:
   - `tests/controllers/` — Integration tests for HTTP handlers.
   - `tests/services/` — Integration tests for complex business logic flows.
   - `tests/middlewares/` — Integration tests for custom middlewares.

6. **⚡ Parallel Testing (`t.Parallel()`)**:
   - **Unit Tests**: Always call `t.Parallel()` at the top of your test functions to run tests concurrently and speed up validation.
   - **Integration Tests**: 
     - ⚠️ **Caution**: Do **not** use `t.Parallel()` if tests execute write/update/delete mutations on a shared database or write to the same Redis keys, as this will lead to race conditions or transaction deadlocks.
     - If you *must* run integration tests in parallel, ensure they use isolated transactions that rollback, or write records with unique dynamic keys (e.g. appending a random UUID to user emails).
   - **Table-Driven Tests**: In table-driven tests, call `t.Parallel()` inside the subtest loop. Make sure to bind the loop variable to avoid closure issues:
     ```go
     for _, tc := range tests {
         tc := tc // Bind variable (good practice, required pre-Go 1.22)
         t.Run(tc.name, func(t *testing.T) {
             t.Parallel()
             // run assertion
         })
     }
     ```

## 🏃 Running Tests

### Run All Tests
```bash
make test
```
*Alternatively, run directly:*
```bash
go test -v ./...
```

### Run a Specific Test
```bash
go test -v ./tests -run TestHealthCheck
```
